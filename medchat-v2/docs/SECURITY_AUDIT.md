# Аудит безопасности: MedChat v1 vs MedChat v2

Дата аудита: ноябрь 2026. Сравнивается `medchat/` (v1, архивная версия) и `medchat-v2/` (актуальная).

## Резюме

v2 не уступает v1 ни в одной категории безопасности и превосходит её в аутентификации, разграничении прав, защите от подбора пароля, аудите и управлении доступом. Сквозное шифрование сообщений, которое было главной сильной стороной v1, в v2 сохранено (X25519 + XSalsa20-Poly1305/secretbox, tweetnacl). Дополнительно в v2 исправлены три критических дефекта, найденных этим аудитом (см. ниже).

## Сравнение по категориям

| Категория | MedChat v1 | MedChat v2 | Вывод |
|---|---|---|---|
| Идентификация сторон | Нет: клиент сам заявляет любой `doctorId`/`patientId`, сервер верит на слово | JWT + учетные записи в БД, проверка статуса, пароли bcrypt (cost 12) | v2 строго лучше |
| Подтверждение врачей | Отсутствует | Код клиники + подтверждение администратором (`invitationStatus`) | v2 строго лучше |
| Разграничение прав (RBAC) | Нет ролей | 4 роли + middleware `authorize`, проверка принадлежности к клинике | v2 строго лучше |
| Сквозное шифрование | X25519 + secretbox (клиентские ключи) | То же + ключи в профилях пользователей, поля `isEncrypted`, `encryptionKeyId` | Паритет |
| Защита от подбора пароля | Нет паролей вообще | Глобальный rate limit + отдельный лимит 10 попыток / 15 мин на `/api/auth` | v2 строго лучше |
| Rate limiting | Token bucket в памяти одного процесса; счетчики обнуляются каждые 60 сек | Redis-хранилище (fallback в память), стандартные заголовки, `passOnStoreError` | v2 лучше |
| Заголовки безопасности | helmet | helmet + compression + явный CORS с allowlist | v2 не хуже |
| Логирование и аудит ошибок | Winston, лог соединений | Структурированные логи + requestId, модель `AuditLog`, errorHandler с контекстом запроса | v2 строго лучше |
| Хранение данных | Ничего не хранит (приватность по архитектуре) | PostgreSQL/MinIO, файлы с TTL 3 дня, сессии, refresh-токены с отзывом | Осознанный компромисс: приватность сохранена за счет E2E-шифрования содержимого; метаданные защищены контролем доступа |
| Отзыв доступа | Только разрыв WS-соединения | Отзыв refresh-токенов, статус аккаунта (`banned`), сессии в БД | v2 строго лучше |
| TLS | Опционально, при отсутствии сертификата тихо падает до HTTP | Terminated на reverse-proxy (см. DEPLOYMENT.md), дефолт dev-режима | v2 не хуже |

## Найденные дефекты v2 и их исправление (текущая итерация)

| # | Дефект | Серьезность | Статус |
|---|---|---|---|
| 1 | `errorHandler.js` использовал `logger` без импорта: при любой ошибке middleware само падало, клиент получал сбой вместо JSON | Критическая | Исправлено: единый модуль `src/utils/logger.js` с fallback на `global.logger`/console; покрыто юнит-тестами с проверкой факта логирования |
| 2 | `index.js` монтировал middleware-модули как объекты (`app.use(authMiddleware)`, `app.use(errorHandler)`, `app.use(rateLimiter)`) — Express падал при старте сервера | Критическая (блокер запуска) | Исправлено: монтируются функции `authMiddleware.authenticate`, `errorHandler.errorHandler`, деструктурированный `rateLimiter` |
| 3 | `rate-limit-redis` не был в зависимостях, но требовался в `rateLimiter.js` — `MODULE_NOT_FOUND` при старте | Критическая | Исправлено: зависимость добавлена; хранилище создается с fallback на in-memory |
| 4 | Swagger падал при отсутствии `docs/api.yaml` | Средняя | Исправлено: fail-safe подключение |
| 5 | `authService.forgotPassword` возвращал ссылку сброса в dev-режиме | Низкая (dev-only) | Принято: только при `NODE_ENV=development`; в продакшене скрыто. Рекомендуется отправка по email |

Автотесты, закрывающие регресс: `tests/errorHandler.test.js` (ответы 4xx/5xx, маскирование сообщения в production, наличие контекста в логах, `wrapAsync`), `tests/integration/auth.test.js` (вход, отказ непроверенному врачу, отсутствие утечки `passwordHash`/`privateKey`, валидация Joi, коды клиник).

## Остаточные риски и рекомендации

1. **Socket.IO принимает соединения без токена** (для «публичных комнат»). Рекомендация: запретить анонимные соединения, проверять участие в чате при `joinChat`.
2. **JWT-секрет из окружения** — обязать длинный секрет при `NODE_ENV=production` (fail-fast), рассмотреть ротацию ключей.
3. **Криптопримитивы не сертифицированы** (tweetnacl: X25519, XSalsa20-Poly1305). Закон 152-ФЗ не требует ГОСТ-алгоритмов, но для ГИС/УЗ-1 и для подписи e-рецептов рекомендуется модуль ГОСТ Р 34.10-2012 / 34.12-2015 (например, через КриптоПро) как следующий этап.
4. **Приватный ключ пользователя хранится в БД** (для E2E) — рассмотреть шифрование на уровне колонки ключом приложения или хранение только на клиенте.
5. **Файлы**: TTL 3 дня задан в модели; требуется cron-задача фактического удаления объектов в MinIO и мониторинг её выполнения.
6. **2FA** описана в модели (`twoFactorEnabled`), но не включена в UI — включить для ролей врача и администратора клиники.

## Соответствие законодательству и стандартам РФ (v2)

| Требование | Норма | Реализация в v2 |
|---|---|---|
| Согласие на обработку ПДн | 152-ФЗ | Явное согласие при регистрации (`consentGiven`, версия согласия), экран согласия в приложении |
| Врачебная тайна | 323-ФЗ, ст. 13 | E2E-шифрование, RBAC, аудит доступа, TTL файлов |
| Минимизация данных | 152-ФЗ | Пациент идентифицируется логином (`patientNumber`), необязательные поля опущены |
| Уровень защищенности ИСПДн | ПП РФ №1119, ФСТЭК №21 | УЗ-1/УЗ-2: контроль доступа, аудит, шифрование; для формализации требуются сертифицированные СКЗИ (см. рекомендации) |
| Идентификация пользователей мессенджера | 149-ФЗ, ст. 10.1 | Не реализовано — обязательный шаг перед публичным запуском (идентификация через Госуслуги/оператора связи) |
| Платежные функции | ГОСТ Р 57580.1-2017 | Микроплатежи на тестовом балансе; при подключении реальных шлюзов обеспечить соответствие |
| Системы ИИ (планируемый ассистент) | ГОСТ Р 59276-2020, 59277-2020 | Учитывать при внедрении ИИ-ассистента |
| Электронная подпись e-рецептов | 63-ФЗ, ГОСТ Р 34.10-2012 | Подпись рецепта реализована на уровне протокола (`isSigned`); сертифицированная ЭП — следующий шаг |

## Вывод

v2 **не хуже v1 по безопасности ни в одном пункте и лучше по всем инженерным категориям**: реальная аутентификация вместо «доверия на слово», подтверждение врачей клиникой, RBAC, защита от брутфорса, централизованное логирование и аудит. Критические дефекты, найденные аудитом в текущей итерации (отсутствие импорта логгера, монтаж middleware-объектов, отсутствие зависимости rate-limit-redis), исправлены и закрыты автотестами в CI.
