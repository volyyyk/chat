## 2. Уровень защищенности ИСПДн

Медицинские данные относятся к специальной категории ПДн (здоровье).
При автоматизированной обработке с передачей по интернету система
классифицируется как **ИСПДн уровня защищенности УЗ-1** (или УЗ-2 при
обработке сотрудников клиники без спецкатегорий):

- межсетевое экранирование и сегментация (firewall, приватные сети Docker);
- управление доступом (JWT + refresh-ротация, роли: patient / doctor / clinic_admin / system_admin);
- регистрация событий безопасности (журналы Winston, requestLogger; тела сообщений не логируются);
- защита каналов связи (TLS 1.2+ на обратном прокси, WSS для WebSocket; в проде — TRUST_PROXY за прокси);
- криптографическая защита: пароли — bcrypt cost 12; содержимое сообщений:
  E2E-конверты хранятся как шифротекст, который сервер **не может расшифровать**;
  серверное AES-шифрование при хранении применяется к plaintext-сообщениям
  (fallback-режим без ключей у участников) и другим полям; резервные копии —
  с шифрованием по паролю пользователя.

**Сквозное (E2E) шифрование содержимого сообщений реализовано** (с ноября
2026; контракт и ограничения — [readme_for_AI.md](./readme_for_AI.md), раздел
E2E). Клиент шифрует текст **на устройстве** (X25519 + NaCl box через
tweetnacl); сервер получает и хранит только шифротекст (конверт в
Message.metadata, поле content пустое, plaintext в БД отсутствует). Сервер
видит только метаданные: участников, время, размер конверта. Роли
clinic_admin / system_admin **не являются участниками E2E-переписки** и не
могут расшифровать содержимое — это осознанное свойство end-to-end модели.

Честно задокументированные ограничения текущей реализации:

1. Если у какого-либо участника чата нет зарегистрированного ключа, клиент
   автоматически отправляет plaintext (graceful fallback) — доступность
   важнее, но такой чат не защищен E2E.
2. Приватные ключи хранятся в аппаратно-защищённом хранилище устройства
   (expo-secure-store: iOS Keychain / Android Keystore,
   keychainAccessible WHEN_UNLOCKED_THIS_DEVICE_ONLY) с прозрачной миграцией
   из AsyncStorage; fallback на AsyncStorage остаётся только на платформах
   без secure storage (например, expo web). При промышленной эксплуатации
   убедиться, что на целевых платформах используется именно secure store.
3. Метаданные (граф общения, время, размеры) серверу видны — это не скрываемый
   канал; при требованиях к скрытию метаданных нужен Double Ratchet + padding
   (этап 7 ROADMAP_NATIVE.md).
4. Файлы и голосовые сообщения пока передаются в обычном контуре (не в
   E2E-конвертах) — в roadmap.

Оператор обязан учитывать остаточные ограничения (пп. 1-4) в модели угроз до
запуска; дальнейшее ужесточение (Double Ratchet, ГОСТ СКЗИ) — этап 7 в
[ROADMAP_NATIVE.md](./ROADMAP_NATIVE.md).

## 3. Требования 152-ФЗ: как реализовано

| Требование | Реализация |
|---|---|
| Согласие субъекта ПДн | Экран ConsentScreen: явное согласие + ФИО + дата, хранится на устройстве и передается при создании чата |
| Уведомление Роскомнадзора | Необходимо подать до начала обработки (см. DEPLOYMENT.md, раздел «Регуляторные шаги») |
| Локализация баз данных | PostgreSQL размещается на серверах в РФ (требование 242-ФЗ, ст. 18) |
| Минимизация данных | Пациент идентифицируется уникальным логином, без обязательной регистрации ФИО |
| Цели обработки | Указаны в оферте и политике конфиденциальности |
| Права субъекта | Экспорт и удаление данных реализованы в API (/api/users/me, /api/backups/export) |
| Хранение не дольше необходимого | Файлы врача автоматически удаляются через 3 дня (cron fileCleanupService) |
| Обработка спецкатегорий | Только с явного согласия; содержимое сообщений защищено E2E-шифрованием (см. §2), транспорт — TLS |
| Реагирование на утечки | Регламент incidents-ответа обязателен оператору (ст. 21.1 152-ФЗ: уведомление РКН в 24 ч при вреде субъектам) |

## 4. Врачебная тайна (323-ФЗ, ст. 13)

- Доступ врача к переписке только его собственных пациентов (проверка
  участника чата на сервере, canAccessChat; Socket.IO joinChat в чужую комнату → forbidden).
- Содержимое E2E-сообщений сервер не расшифровывает никогда; plaintext
  fallback-сообщения шифруются при хранении; тела сообщений не пишутся в логи.
- Файлы с видимостью doctor_only недоступны другим врачам и клинике.
- Роль clinic_admin не имеет доступа к содержимому сообщений (только метаданные чатов).
- Разграничение выполняется и на уровне приложения/БД, и криптографически:
  содержимое E2E-сообщений доступно только участникам переписки (см. §2).

## 5. Особенности для мессенджеров и медсервисов

- **Оферта (ст. 437 ГК РФ)**: docs/OFFER.md, акцепт при регистрации/согласии.
- **Правила оказания телемедицинских услуг** (Приказ Минздрава № 965н и
  323-ФЗ, ст. 36.2): чат не является телемедицинской консультацией;
  интерфейсы содержат дисклеймер; видеоконсультации требуют отдельной
  интеграции с медорганизацией.
- **Идентификация пользователей (149-ФЗ, ст. 10.1)**: для промышленной
  эксплуатации мессенджера в РФ требуется идентификация пользователей
  (абонентский номер / учетная запись Госуслуг). В текущей версии
  отсутствует — обязательный этап перед прод-запуском (ROADMAP, этап 7).
- **Платные услуги**: микротранзакции реализованы через тестовый баланс.
  Подключение реальных платежей потребует 54-ФЗ (онлайн-касса, фискальные
  чеки), договора эквайринга и отражения в оферте.
- **Реклама и отзывы**: отзывы пациентов проходят модерацию (модель Review,
  флаг isApproved); при размещении рекламы — маркировка по закону о рекламе.

## 6. Что требуется от оператора перед запуском

1. Определить оператора ПДн (юридическое лицо) и опубликовать политику.
2. Подать уведомление об обработке ПДн в Роскомнадзор.
3. Оценить угрозы и присвоить уровень защищенности (Приказ № 996),
   аттестовать систему по УЗ-1 (Приказ ФСТЭК № 21); при требованиях ГОСТ-крипто —
   сертифицированные СКЗИ (см. ROADMAP, блок C/C++).
4. Внедрить идентификацию пользователей (149-ФЗ ст. 10.1) и регламент
   реагирования на инциденты ИБ, включая уведомление РКН об утечках (24 ч).
5. Заключить договоры с клиниками (обработка ПДн по поручению).
6. Хранить журналы доступа к спецкатегориям ПДн.
